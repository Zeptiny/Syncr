# Syncr 2.2.0

Syncr 2.2 **backs up a folder of a remote**: your Nextcloud photos, a
bucket, an SFTP share, straight into a restic repository, through a
mirror the worker keeps up to date or through `rclone mount`. Snapshots of
a remote are named after it, and an emptied folder fails instead of
pushing your real snapshots out of retention. Schedules also check a job's
local folders against the worker before they are saved. Nothing changes
for existing jobs, schedules and backups.

## Upgrade

- **Controller:** back up the database, then pull the new image (`docker
  compose pull && docker compose up -d`) or replace the binary
  ([running the controller](../deployment.md#upgrading)). No database
  migration and no new setting.
- **Workers:** a 2.1 worker keeps running every job it ran before, but it
  cannot back up a remote, so against a 2.2 controller it shows the
  **Outdated** badge, and a backup of a remote sent to it fails with
  `worker_outdated`. Upgrade it with the command on its page,
  `syncr-worker upgrade` ([upgrading](../upgrade.md)). The upgraded worker
  keeps using rclone 1.75.2 and restic 0.19.1. A worker in a container is
  upgraded by pulling its new image.
- **The mirror needs nothing new,** only disk in the worker's data
  directory, as much as the folders it mirrors (after their filters).
- **The mount needs FUSE 3 or WinFsp,** set up outside Syncr. Nothing
  breaks without it: the worker reports why it cannot mount, and the
  editor offers the mirror.

  | Install | What to do for the mount |
  |---|---|
  | Linux, system service | `apt install fuse3` (or `dnf install fuse3`), restart the worker |
  | Linux, `--user` service | `fuse3`, plus a drop-in with `NoNewPrivileges=no` ([setup](../setup-linux.md#backing-up-remotes-with-the-mount-method)) |
  | Docker | the worker image now ships `fuse3`; uncomment `devices: [/dev/fuse]`, `cap_add: [SYS_ADMIN]` and `security_opt: [apparmor:unconfined]` in the compose file's worker service ([deployment](../deployment.md#mounting-remotes-in-a-container)) |
  | LXC | pass `/dev/fuse` through from the host, or use the mirror |
  | Windows | install [WinFsp](../setup-windows.md#backing-up-remotes-with-the-mount-method), restart the worker |

- **A new folder in the data directory,** `<data_dir>/sources`, holds the
  mirrors and mount points. No job, folder listing or folder size may use
  it, even when `local_roots` covers the data directory; a backup or copy
  of a folder that holds it (such as `/`) now leaves it out.

| Release file | What it is |
|---|---|
| `syncr-worker_linux_amd64.tar.gz`, `syncr-worker_linux_arm64.tar.gz`, `syncr-worker_windows_amd64.zip` | the worker |
| `syncr-controller_linux_amd64.tar.gz`, `syncr-controller_linux_arm64.tar.gz`, `syncr-controller_windows_amd64.zip` | the controller, with the web UI built in |
| `checksums.txt` | SHA-256 of every archive |

The archives carry GitHub build provenance:
`gh attestation verify <file> --owner Zeptiny`. Images are tagged `2.2.0`,
`2.2`, `2` and `latest`, for linux/amd64 and linux/arm64.

## What's new

### Back up a folder of a remote
- A backup's **What to back up** offers **A folder on a remote**: one of
  your remotes and a folder of it, instead of folders of the worker
  ([restic](../restic.md#back-up-a-folder-of-a-remote)). In a remote's file
  browser, **New job, Back up this folder…** opens it filled in.
- **How the worker reads it:**
  - **Mirror** (the default) keeps a copy of the folder on the worker,
    brought up to date with `rclone sync` before each backup, so a run
    downloads only what changed. It works on every worker and takes disk;
    **Delete the mirror after each run** trades the disk for a full
    download each time. Mirrors nobody used for 30 days are deleted.
  - **Mount** reads the folder through a read-only `rclone mount` for the
    length of the job: no disk, but FUSE 3 on Linux or WinFsp on Windows.
    The mount is removed however the job ends, and one left by a killed
    worker is removed at its next start.
- **rclone filter rules** leave files out in both methods, so a mirror
  never downloads what is skipped. Bandwidth limit, parallel downloads and
  fast listing are there too.
- **Snapshots of a remote** hold the folder's contents at their root and
  carry the tag `syncr-remote:<remote id>`: the snapshot list, the
  snapshot browser and the restore sheet show **From *remote name*** and a
  badge, and a retention job can select them by the tag. They restore to a
  folder of a worker (then a Copy job puts them back on a remote);
  **Restore to original location** is not offered for them.
- **One worker:** a backup of a remote keeps its mirror or mount folder on
  one worker, so its schedule targets a worker, not a label. A run on
  another worker reads everything once and is a retention group of its
  own.
- **An empty folder fails** with *The remote folder is empty*
  (`source_empty`, a new error code) before the mirror is touched, so an
  emptied or mistyped folder does not push real snapshots out of
  retention. **Back up an empty folder** lets it pass; restic makes no
  empty snapshot, so such a run succeeds without one and says so.
- A backup that would read its own repository (the same remote, one folder
  inside the other) is refused, and so is a Local directory remote (back
  up that folder of the worker instead).
- **Dry run** brings the mirror up to date for real and runs restic with
  `--dry-run`.
- **The job page** shows the phase (*Mirroring…*, then *Backing up…*), and
  the summary adds how the folder was read and what the mirror downloaded
  and deleted. The throughput chart marks where the counters restart, and
  a finished job's legend shows its average.
- **Workers say what they can do:** the Workers page and each worker's
  page show **Remote backups**, "Mirror ✓ · Mount ✗ – /dev/fuse is
  missing", from a check the worker makes at startup (including a trial
  mount). Job and schedule forms disable a worker or a method that cannot
  work, with the reason. The worker's configuration gains a
  `remote_sources` block ([worker configuration](../worker-config.md#remote-sources)).
- The API ([API](../api.md)): `ResticBackupDefinition.remote_source`,
  `WorkerInfo.remote_sources`, `JobProgress.phase`, the error code
  `JOB_ERROR_CODE_SOURCE_EMPTY` (32) and the worker feature
  `restic.remote_source`. Hooks see the new code in
  `SYNCR_JOB_ERROR_CODE`.
- Design record: [ADR 0020](../adr/0020-backing-up-a-remote.md).

### Schedules and local folders
- In the schedule form, **Where it runs** now comes right after the job's
  kind, before any folder, so **Browse** works while you type a new
  schedule's folders. Transfers and two-way syncs on a label browse the
  label's first online worker, as backups did, and every kind says why
  Browse is missing when it is.
- A local folder outside the allowed folders (`local_roots`) of the
  workers a job or schedule may run on gets a warning under the field. It
  never blocks saving (the worker, which resolves links, decides), but a
  schedule no longer saves silently and then fails its first run with
  `path_not_allowed`.

### Fixes
- A worker that shuts down hands the jobs waiting in its queue back to the
  controller. A late message from the stopping process could mark them as
  started again on that process, where they stayed until its next start,
  or until they ended `worker_lost` an hour later. The controller now
  sends a stopping process nothing new and ignores its late start
  messages.

## Known limitations

- A snapshot of a remote cannot be restored straight back to the remote:
  restore it to a worker folder, then copy it.
- Schedules of a backup of a remote cannot target a label (mount over
  labels needs a retention grouping that is not there yet), and a backup
  reads one remote folder, without worker folders beside it.
- Through a mount, a remote without stable modification times (some
  WebDAV servers) makes every file look changed, so everything is read
  again on each run; the mirror keeps its own times.
- On S3 and compatibles, a missing folder in an existing bucket looks
  empty, so it fails as empty rather than missing. A remote that does not
  answer at all makes the run wait out rclone's retries (about 12 minutes)
  before it fails.
- restic's own command line shows a snapshot of a remote with the worker's
  mirror or mount folder as its path; the UI shows the remote.
- A backup that reads its own repository through a union, an alias or a
  second remote for the same storage is not detected.
- On Windows a mirror keeps rclone's encoding of names Windows cannot hold
  (fullwidth look-alikes), and so does the snapshot.
- The throughput chart of a finished backup of a remote shows the restart
  of the counters, but stored progress samples do not record which phase
  they belong to.
- Saving a schedule on a worker that cannot use the chosen method only
  shows in the worker picker; the schedule's runs then fail with
  `tool_unavailable` and the reason.
- Everything listed for [2.1.0](v2.1.0.md#known-limitations) still applies.

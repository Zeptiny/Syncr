# Syncr 2.3.0

Syncr 2.3 adds **encrypted remotes**: a remote that encrypts files on the
worker, with rclone crypt, and stores them in a folder of another of your
remotes, so a bucket or a server only ever holds encrypted names and
contents. Copy, sync and two-way sync into and out of it, browse it, and
back it up like any remote. Nothing changes for existing remotes, jobs,
schedules and backups.

## Upgrade

- **Controller:** back up the database, then pull the new image (`docker
  compose pull && docker compose up -d`) or replace the binary
  ([running the controller](../deployment.md#upgrading)). One database
  migration (00012) runs at start: remotes get two columns for where an
  encrypted remote stores its data, empty for every remote already there.
  No new setting.
- **Downgrading** to 2.2 means restoring the database backup made before
  the upgrade, as for every release ([upgrading](../upgrade.md)). Undoing
  migration 00012 instead (its down script, with goose) needs every
  encrypted remote deleted first: it would lose where their data is stored,
  so it refuses while one exists (*cannot undo migration 00012: N encrypted
  remote(s) store their data in other remotes…*). Their stored files stay
  where they are; keep the passwords to read them later.
- **Workers:** a 2.2 worker keeps running every job it ran before, but it
  cannot use encrypted remotes, so against a 2.3 controller it shows the
  **Outdated** badge. **Upgrade your workers to use encrypted remotes:** a
  job on one sent to an older worker fails with `worker_outdated`, and
  folder listings, remote tests and folder sizes of an encrypted remote
  only use upgraded workers. Upgrade with the command on the worker's
  page, `syncr-worker upgrade` ([upgrading](../upgrade.md)). The upgraded
  worker keeps using rclone 1.75.2 and restic 0.19.1.
- **Schedules on a label** with workers of both versions behind it can
  pick an older one for a job on an encrypted remote, which then fails
  with `worker_outdated`. Upgrade every worker of the label.

## What's new

### Encrypted remotes
- **Remotes, Add remote, Encrypted (crypt)**: choose **Store in** (one of
  your remotes and a folder on it, with **Browse**), a password, an
  optional salt and how names are encrypted
  ([encrypted remotes](../encrypted-remotes.md)). The worker encrypts
  contents and names before anything leaves it, and decrypts them when it
  reads; the remote you store in only holds encrypted data.
- **The password is shown once.** The form warns that nobody can read the
  files without it, **Generate** makes a random 32-character password in
  your browser with a copy button, and **Create** waits until you tick
  that you saved it somewhere else.
- **The password, the salt and the name settings are fixed** after
  creation: the edit page shows them locked, with why. Another value would
  make the stored files unreadable. The name and **Store in** can change.
- **Everywhere a remote works:** copy, sync and move, two-way sync, the
  file browser, folder sizes, **Test remote**, and backups of a folder of
  it (mirror or mount). Restic repositories cannot be on an encrypted
  remote (restic encrypts already); put them on the remote it stores in.
- **No checksums:** an encrypted remote keeps none, so transfers and
  two-way syncs with an encrypted side do not offer checksum comparison
  ("This remote keeps no checksums"), and the API refuses it.
- **A wrong password is caught before anything changes.** Before a copy,
  sync, move, two-way sync or backup uses an encrypted remote, from it or
  into it, and before **Test remote** or the file browser lists it, the
  worker reads the first bytes of one of its files, which must decrypt.
  With a wrong password the job fails with `execution_failed` (*…its
  password is wrong…*), whatever the name settings, the folder or the
  storage: nothing is copied, deleted or overwritten. Without the check,
  obfuscated names on S3 or B2 would let a sync from the remote's root
  empty its destination. A remote that holds no file with data has nothing
  to check. (The password is fixed, so a wrong one only happens with a
  second encrypted remote over the same folder.)
- **A missing folder of an encrypted remote** fails with `not_found`, also
  on S3 and B2, where a missing folder of a plain bucket is an empty
  source.
- **Two-way syncs** with an encrypted side keep their state and wait for
  each other by the folder the data is stored in, and a backup of an
  encrypted folder stored inside its own repository's folder is refused
  when you save it.
- **Reading the data without Syncr:** it is ordinary rclone crypt data;
  the docs give the rclone configuration to read it with the same
  settings.
- The API ([API](../api.md)): `RemoteInput.wrapped`, `Remote.wrapped` and
  `Remote.wrapped_by`, `BackendField.fixed`, the capabilities `wrapper` and
  `no_checksum`, the field kind `FIELD_KIND_WRAPPED` and the worker feature
  `rclone.crypt`.
- Design record: [ADR 0021](../adr/0021-wrapper-remotes.md).

### Remotes
- The Remotes list's **In unions** column is now **Used by**: the unions a
  remote is a member of and the encrypted remotes stored in it. An
  encrypted remote shows where it stores its data ("in *B2 offsite* /
  vault").
- **Deleting a remote that is in use** names everything that holds it: the
  repositories on it, the encrypted remotes stored in it and the unions it
  is a member of, with **Delete** disabled. It used to name only the first.

### Fixes
- Following a running job could show one progress sample twice, when the
  worker reported it just as the page opened. Live progress now never
  repeats a sample.

## Known limitations

- An encrypted remote cannot store its data in a worker's local folder, a
  union or another encrypted remote, and cannot be a union member.
- The password check needs a file with data: a remote that holds none
  (nothing yet, or only empty files) is not checked. With obfuscated names
  and a wrong password, a sync from it can then replace its destination's
  copies of those empty files with garbled names.
- Folder sizes do not check the password: with a wrong one, a folder of an
  encrypted remote on S3 or B2 may count as empty.
- Every job and listing on an encrypted remote runs rclone once more for
  the check (a short listing and a read of at most 64 KiB).
- Changing a password means a new encrypted remote and a copy job.
- Progress of a copy into an encrypted remote counts encrypted bytes,
  slightly more than the files' sizes.
- Changing **Store in** while jobs wait in the queue leaves them waiting
  for the old folder's jobs.
- Everything listed for [2.2.0](v2.2.0.md#known-limitations) still applies.

# Syncr 2.3.0

Syncr 2.3 adds **encrypted remotes**: a remote that encrypts files on the
worker, with rclone crypt, and stores them in a folder of another of your
remotes, so a bucket or a server only ever holds encrypted names and
contents. Copy, sync and two-way sync into and out of it, browse it, and
back it up like any remote. Nothing changes for existing remotes, jobs,
schedules and backups.

It also adds **more remote types**: SMB shares, FTP and FTPS servers,
Azure Blob Storage and Google Cloud Storage, and twelve more S3 providers.
And the controller now carries its **documentation**: these guides and
notes under **Docs**, searchable, with help links from the pages they
explain.

## Upgrade

- **Controller:** back up the database, then pull the new image (`docker
  compose pull && docker compose up -d`) or replace the binary
  ([running the controller](../deployment.md#upgrading)). One database
  migration (00012) runs at start: remotes get two columns for where an
  encrypted remote stores its data, empty for every remote already there.
  No new setting.
- **Downgrading** to 2.2 means restoring the database backup made before
  the upgrade, as for every release ([upgrading](../upgrade.md)). Undoing
  migration 00012 instead (its down script, with goose) needs every
  encrypted remote deleted first: it would lose where their data is stored,
  so it refuses while one exists (*cannot undo migration 00012: N encrypted
  remote(s) store their data in other remotes…*). Their stored files stay
  where they are; keep the passwords to read them later.
- **Workers:** a 2.2 worker keeps running every job it ran before, but it
  cannot use encrypted remotes, so against a 2.3 controller it shows the
  **Outdated** badge. **Upgrade your workers to use encrypted remotes:** a
  job on one sent to an older worker fails with `worker_outdated`, and
  folder listings, remote tests and folder sizes of an encrypted remote
  only use upgraded workers. Upgrade with the command on the worker's
  page, `syncr-worker upgrade` ([upgrading](../upgrade.md)). The upgraded
  worker keeps using rclone 1.75.2 and restic 0.19.1.
- **Workers must be upgraded to use the new types** (SMB, FTP/FTPS, Azure
  Blob Storage, Google Cloud Storage), as for encrypted remotes: a job on
  one sent to a 2.2 worker fails with `worker_outdated`, and folder
  listings, remote tests and folder sizes of such a remote only use
  upgraded workers. The new S3 providers work on every worker. A schedule
  on a label with workers of both versions behind it can pick an older one
  for such a job: upgrade every worker of the label.
- **Schedules on a label** with workers of both versions behind it can
  pick an older one for a job on an encrypted remote, which then fails
  with `worker_outdated`. Upgrade every worker of the label.

`gh attestation verify <file> --owner Zeptiny`. Images are tagged `2.3.0`,
`2.3`, `2` and `latest`, for linux/amd64 and linux/arm64.

## What's new

### Encrypted remotes
- **Remotes, Add remote, Encrypted (crypt)**: choose **Store in** (one of
  your remotes and a folder on it, with **Browse**), a password, an
  optional salt and how names are encrypted
  ([encrypted remotes](../encrypted-remotes.md)). The worker encrypts
  contents and names before anything leaves it, and decrypts them when it
  reads; the remote you store in only holds encrypted data.
- **The password is shown once.** The form warns that nobody can read the
  files without it, **Generate** makes a random 32-character password in
  your browser with a copy button, and **Create** waits until you tick
  that you saved it somewhere else.
- **The password, the salt and the name settings are fixed** after
  creation: the edit page shows them locked, with why. Another value would
  make the stored files unreadable. The name and **Store in** can change.
- **Everywhere a remote works:** copy, sync and move, two-way sync, the
  file browser, folder sizes, **Test remote**, and backups of a folder of
  it (mirror or mount). Restic repositories cannot be on an encrypted
  remote (restic encrypts already); put them on the remote it stores in.
- **No checksums:** an encrypted remote keeps none, so transfers and
  two-way syncs with an encrypted side do not offer checksum comparison
  ("This remote keeps no checksums"), and the API refuses it.
- **A wrong password is caught before anything changes.** Before a copy,
  sync, move, two-way sync or backup uses an encrypted remote, from it or
  into it, and before **Test remote** or the file browser lists it, the
  worker reads the first bytes of one of its files, which must decrypt.
  With a wrong password or salt the job fails with `execution_failed`
  (*…its password is wrong…*), in every name mode, whatever the folder or
  the storage: nothing is copied, deleted or overwritten. A few files in
  the remote's folder that it did not write, or damaged ones, do not fail
  the check (up to two before the first file that decrypts). Without the check,
  obfuscated names on S3 or B2 would let a sync from the remote's root
  empty its destination. A remote that holds no file with data has nothing
  to check. (The password is fixed, so a wrong one only happens with a
  second encrypted remote over the same folder.) Such a second remote must
  use exactly the same password, salt and name settings: with "Encrypt
  folder names" off over data written with it on, or suffix `none` over
  `.bin`, the check passes and a sync into it deletes the first remote's
  files. The docs say what to check.
- **A missing folder of an encrypted remote** fails with `not_found`, also
  on S3 and B2, where a missing folder of a plain bucket is an empty
  source.
- **Two-way syncs** with an encrypted side keep their state and wait for
  each other by the folder the data is stored in, and a backup of an
  encrypted folder stored inside its own repository's folder is refused
  when you save it.
- **Reading the data without Syncr:** it is ordinary rclone crypt data;
  the docs give the rclone configuration to read it with the same
  settings.
- The API ([API](../api.md)): `RemoteInput.wrapped`, `Remote.wrapped` and
  `Remote.wrapped_by`, `BackendField.fixed`, the capabilities `wrapper` and
  `no_checksum`, the field kind `FIELD_KIND_WRAPPED` and the worker feature
  `rclone.crypt`.
- Design record: [ADR 0021](../adr/0021-wrapper-remotes.md).

### More remote types
- **Remotes, Add remote** lists four new types, each with its own icon
  ([remotes](../remotes.md), every type and what to enter):
  - **SMB (Windows share)**: a share on a Windows computer, a Samba server
    or a NAS; host, user (`guest` for guest shares), password, and the
    share with an optional folder. SMB does not verify the server's
    identity: use it on networks you trust.
  - **FTP / FTPS**: host, user (`anonymous` for anonymous FTP), password,
    implicit or explicit FTPS, and a base path. Without TLS, the password
    and the files cross the network in clear.
  - **Azure Blob Storage**: a storage account with exactly one sign-in
    method: the account key, a SAS URL, or a service principal (tenant,
    client ID and client secret). The endpoint, for other Azure clouds, is
    the full blob service URL.
  - **Google Cloud Storage**: a service account's JSON key, pasted as it
    is. Its `token_uri` must be absent or Google's own
    (`https://oauth2.googleapis.com/token`). **Uniform bucket-level
    access** is on by default, so uploads work on the buckets the Google
    Cloud console creates (they refuse the ACLs rclone sends otherwise).
- **Workers must be upgraded to use the new types** (see
  [Upgrade](#upgrade)).
- **Twelve more S3 providers:** Akamai / Linode, Alibaba Cloud OSS, Hetzner
  Object Storage, IBM Cloud Object Storage, IDrive e2, IONOS Cloud, MEGA
  S4, OVHcloud, Scaleway, SeaweedFS, Storj S3 gateway and Synology C2.
  The endpoint stays required unless the provider is AWS: without one,
  rclone would send the requests to AWS. The
  [remotes](../remotes.md#amazon-s3-and-compatible) page gives an
  endpoint for each and the region rclone gives with it.
- **No checksums on SMB and FTP:** like encrypted remotes, they keep none,
  so transfers and two-way syncs with such a side do not offer checksum
  comparison and the API refuses it. A union with an SMB or FTP member
  now counts as keeping none too.
- **The worker never uses its host's identity:** a Google Cloud Storage
  remote needs its own key (the worker's Google credentials are never
  used), and an FTP or SMB remote needs a user (the worker's account name
  is never sent). Azure's managed identity, CLI and environment sign-ins
  and its storage emulator are refused, and FTP user names and passwords
  may not contain line breaks.
- The API ([API](../api.md)): the backend types `smb`, `ftp`,
  `azureblob` and `gcs`, and the worker features `rclone.backend.smb`,
  `rclone.backend.ftp`, `rclone.backend.azureblob` and
  `rclone.backend.gcs`.

### Documentation in the controller
- **Docs** in the sidebar opens the user guides, the [API](../api.md) page
  and the release notes inside the controller, for the version it runs:
  the same pages as the `docs/` folder on GitHub, with the contents on the
  left, an **On this page** outline, Previous and Next, and a copy button
  on every command. On a phone the contents open from **Contents**.
- **Readable without signing in,** at `/docs`: the sign-in page links to
  them (**Read the documentation**), and the setup wizard links to where
  the setup code is ([first start](../deployment.md#first-start)) and to
  the worker install guides. Signed in, they open inside the app.
- **Search** (the Search button, or `/` and Ctrl+K or ⌘K on a docs page)
  finds pages and sections as you type: every word must match the start of
  a word, and titles and headings rank first.
- **Help links:** a small **Help** next to a page's title or a panel opens
  the section that explains it, in a new tab, so a half-filled form stays
  as it is. Adding a worker, upgrading one, each remote type, two-way
  sync's safety checks, conflicts and resync, backups, repositories,
  snapshots, restores, the file pages, notifications and API tokens have
  one, and so has the note on remotes that keep no checksums.
- **What's new:** after an upgrade, signed-in users see "Syncr was updated
  to v2.3.0." above the page, with **Read the release notes** and
  **Dismiss**, once per browser and release. A release candidate shares
  the notice of its release; a development build shows none.
- **Pinned to the running version:** the docs say which release they
  describe ("Docs for v2.3.0"). **View on GitHub**, and links to files that
  stay on GitHub (design records, the compose files, the protos), open that
  release's tag, or `main` on a development build.
- The pages are built into the controller with the web UI: nothing is
  fetched from the internet. The controller grows by about 2 MB, mostly
  screenshots.
- Design record: [ADR 0022](../adr/0022-docs-in-the-ui.md).

### Remotes
- The Remotes list's **In unions** column is now **Used by**: the unions a
  remote is a member of and the encrypted remotes stored in it. An
  encrypted remote shows where it stores its data ("in *B2 offsite* /
  vault").
- **Deleting a remote that is in use** names everything that holds it: the
  repositories on it, the encrypted remotes stored in it and the unions it
  is a member of, with **Delete** disabled. It used to name only the first.

### Fixes
- Following a running job could show one progress sample twice, when the
  worker reported it just as the page opened. Live progress now never
  repeats a sample.

## Known limitations

- An encrypted remote cannot store its data in a worker's local folder, a
  union or another encrypted remote, and cannot be a union member.
- The password check needs a file with data: a remote that holds none
  (nothing yet, or only empty files) is not checked. With obfuscated names
  and a wrong password, a sync from it can then replace its destination's
  copies of those empty files with garbled names.
- Folder sizes do not check the password: with a wrong one, a folder of an
  encrypted remote on S3 or B2 may count as empty.
- Every job and listing on an encrypted remote runs rclone once more for
  the check (a short listing and a read of at most 64 KiB).
- With the right password, three foreign or damaged files met before the
  first file that decrypts fail the check (rclone lists a whole folder, or
  on S3 and B2 a batch of 100 files, before reading any of it). A foreign
  file also makes listings of its folder fail, naming it.
- A second encrypted remote over the same data with "Encrypt folder names"
  turned off, or suffix `none` over `.bin`, passes the check: its names
  still decrypt.
- Changing a password means a new encrypted remote and a copy job.
- Progress of a copy into an encrypted remote counts encrypted bytes,
  slightly more than the files' sizes.
- Changing **Store in** while jobs wait in the queue leaves them waiting
  for the old folder's jobs.
- SMB, Azure Blob Storage and Google Cloud Storage are tested with unit
  tests and rclone's option list, not against live servers; FTP is tested
  end to end against rclone's own FTP server.
- On an FTP server that cannot set modification times (no MFMT; on
  vsftpd, turn on **Set times with MDTM**), rclone compares files by size
  only: copies, syncs and two-way syncs see a change only when a file's
  size changes, and a two-way sync warns about it on every run.
- On such a server, a **backup of a folder of the remote with the mirror
  method misses a change that keeps a file's size**: every later snapshot
  keeps the old content, and the job still succeeds. Use the mount method
  (restic sees a change when the server lists a new time), turn on
  **Delete the mirror after each run**, or use SFTP or WebDAV when the
  server offers them ([FTP](../remotes.md#ftp--ftps)).
- Google Cloud Storage takes only service account keys (no user sign-in),
  and neither Azure nor Google Cloud Storage reaches public containers or
  buckets anonymously.
- SMB signs in with a user name and a password only (no Kerberos).
- Transfers, checks, schedules, the dashboard and users have no guide yet,
  so their pages have no help link.
- What's new is remembered per browser, not per user: on a shared browser,
  one user's **Dismiss** hides it for the others.
- Everything listed for [2.2.0](v2.2.0.md#known-limitations) still applies.

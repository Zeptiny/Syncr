# Syncr 2.1.0

Syncr 2.1 adds **two-way sync**: one folder kept in step on several
machines, for example a desktop and a laptop through a Cloudflare R2
bucket. It also adds a **file browser**: select files and folders on a
worker, a remote or in a snapshot, copy or move them, see how big each
folder is, search a repository's snapshots for a file and its versions,
and compare two snapshots. Nothing changes for existing jobs, schedules
and backups.

## Upgrade

- **Controller:** back up the database, then pull the new image (`docker
  compose pull && docker compose up -d`) or replace the binary
  ([running the controller](../deployment.md#upgrading)). The database
  schema does not change. The configuration gains one optional setting,
  `probe.scan_timeout` (45 s), and a reverse proxy in front of the
  controller should now wait **above 60 s** for a response (it was 40 s;
  [deployment](../deployment.md#https-and-reverse-proxies)).
- **Workers:** a 2.0 worker keeps running every job it ran before, but it
  cannot run a two-way sync, so against a 2.1 controller it shows the
  **Outdated** badge. A two-way sync, or a restore to the original
  location, sent to it fails with `worker_outdated`, and it cannot measure
  folders, search snapshots or compare them. Upgrade it with the command on its page,
  `syncr-worker upgrade` ([upgrading](../upgrade.md)). The upgraded worker
  keeps using rclone 1.75.2 and restic 0.19.1.

`gh attestation verify <file> --owner Zeptiny`. Images are tagged `2.1.0`,
`2.1`, `2` and `latest`, for linux/amd64 and linux/arm64.

## What's new

### Two-way sync
- A new job kind, **Two-way sync** (`rclone_bisync`, rclone's `bisync`):
  two folders, each on a worker or on a remote, kept in step in both
  directions. New files, changes and deletions on either side spread to
  the other at the next run. It runs by hand or on a schedule
  ([two-way sync](../bisync.md)).
- **The first run of a pair resyncs on its own:** both folders are merged,
  nothing is deleted, and a file that differs keeps the newer version.
  It never fills an empty folder on the worker, which looks the same as a
  drive that is not mounted: a new machine's empty folder asks for one
  **Resync now** first.
- **Conflicts keep both versions.** A file edited on both sides between two
  runs is kept twice, as `report.docx.conflict1` and
  `report.docx.conflict2`, on both sides; the job lists the conflicts.
  Optionally the newer, older, larger or smaller version, or one side's,
  wins; the other is still kept.
- **Safety checks:** a run that would delete more than half the files of a
  side (the limit can be set), that finds every file changed, an empty
  side, or, optionally, missing `RCLONE_TEST` check files stops before it
  changes anything. The job page explains which check stopped it and,
  where that helps, offers **Run once anyway**.
- **Resync now:** after changed filters, an empty folder on a pair's first
  run, or a critical error before the pair had a state to go back to, the
  pair fails with *Resync required* until someone runs a resync from the
  job's or the schedule's page. After other critical errors, such as a
  file the worker cannot read, the job says what to fix, and the next run
  goes on from the last good state without a resync.
- Two pairs that share a folder (the desktop's and the laptop's, on the
  same bucket path) never run at the same time: one waits for the other,
  marked *Waiting for folder*.
- A pair keeps its state on the worker that runs it, so its schedule
  targets one worker rather than a label. The worker removes the state of
  pairs that have not run for 180 days.
- New error codes: `resync_required`, `safety_abort` and
  `side_unavailable` ([API](../api.md)); hooks see them in
  `SYNCR_JOB_ERROR_CODE`.

### File browser
- **Pages for a worker's folders and for a remote** ([browsing
  files](../browsing.md)), next to the snapshot browser, with the folder
  in the address: sorting by name, size or time, a keyboard to move,
  select and open, ranges with Shift, and **Select all** across every row
  that matches the filter. **Refresh** shows how old a listing is, a
  remote's page shows its usage where the backend can tell, and **Listed
  by** picks the worker that lists a remote or a snapshot.
- **A selection across folders** with a tray: what is selected, the total
  size, and **Copy paths**.
- **Copy and move** a selection into a folder of a worker or a remote, as
  a file manager does: a selected folder arrives as a folder. It runs as a
  transfer job with filters on the worker whose disk is involved, keeps
  existing files by default, can be previewed as a dry run, and a move
  removes only what it moved. The listings refresh when the job ends.
- **Start a job from a selection:** a restic backup of the selected paths,
  a copy or a two-way sync of the open folder, a schedule of any of them,
  or a new repository in a remote's folder, opened in their editors with
  the fields filled in.
- **Folder sizes:** **Calculate sizes** measures the open folder of a
  worker, a remote or a snapshot in one pass and shows each subfolder's
  total, files and share. A walk that takes longer than
  `probe.scan_timeout` stops with what it found, marked "at least".
- **Snapshots:** a switcher to the older or newer snapshot that keeps the
  open folder; a filter, host and tag choices and grouping on the
  snapshot list; **Restore to original location**, which writes the
  selected items back where they were on the snapshot's machine; and the
  last restore target remembered per repository.
- **Search** a repository's snapshots for a name or a path pattern (`restic
  find`), with each file's **versions**: every snapshot that has it,
  grouped by distinct copy, each restorable.
- **Compare** two snapshots, or one folder in both (`restic diff`): what
  was added, removed or changed, with totals, from a snapshot's **Compare
  with previous**.
- Six new API calls ([API](../api.md)).

## Known limitations

- The two paths of a pair may be at most 200 bytes together (rclone names
  its state files after them).
- Nested two-way locations (`R2:shared` and `R2:shared/sub`) and transfers
  into a two-way folder are not kept apart: their runs may overlap.
- One unreadable file stops its pair until it is fixed.
- Two remotes for the same bucket path (one per Syncr user, say) do not
  make their pairs wait for each other, and two definitions of the same
  two folders on a worker share one state.
- On backends without modification times (some WebDAV servers), an edit
  that keeps a file's size is not noticed.
- Two files whose names differ only in case collide on Windows and macOS.
- Changing a remote's settings other than its secret, such as a new access
  key ID after rotating an R2 token, makes the next run of its pairs a
  resync.
- There is no new folder, rename, delete or download in the file
  browser (downloads: [issue #36](https://github.com/Zeptiny/Syncr/issues/36)),
  and no copy straight between two workers' folders (copy through a
  remote).
- Folder sizes, searches and comparisons cannot run longer than
  `probe.scan_timeout` (at most 90 s): a very large tree or bucket gets a
  partial answer, and each worker runs one of them at a time.
- Comparisons do not report changes of metadata alone (modification time,
  permissions).
- Everything listed for [2.0.0](v2.0.0.md#known-limitations) still applies.

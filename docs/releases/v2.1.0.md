# Syncr 2.1.0

Syncr 2.1 adds **two-way sync**: one folder kept in step on several
machines, for example a desktop and a laptop through a Cloudflare R2
bucket. Nothing changes for existing jobs, schedules and backups.

## Upgrade

- **Controller:** back up the database, then pull the new image (`docker
  compose pull && docker compose up -d`) or replace the binary
  ([running the controller](../deployment.md#upgrading)). The database
  schema does not change, and neither does the configuration.
- **Workers:** a 2.0 worker keeps running every job it ran before, but it
  cannot run a two-way sync, so against a 2.1 controller it shows the
  **Outdated** badge. A two-way sync sent to it fails with
  `worker_outdated`. Upgrade it with the command on its page,
  `syncr-worker upgrade` ([upgrading](../upgrade.md)). The upgraded worker
  keeps using rclone 1.75.2 and restic 0.19.1.

| Release file | What it is |
|---|---|
| `syncr-worker_linux_amd64.tar.gz`, `syncr-worker_linux_arm64.tar.gz`, `syncr-worker_windows_amd64.zip` | the worker |
| `syncr-controller_linux_amd64.tar.gz`, `syncr-controller_linux_arm64.tar.gz`, `syncr-controller_windows_amd64.zip` | the controller, with the web UI built in |
| `checksums.txt` | SHA-256 of every archive |

The archives carry GitHub build provenance:
`gh attestation verify <file> --owner Zeptiny`. Images are tagged `2.1.0`,
`2.1`, `2` and `latest`, for linux/amd64 and linux/arm64.

## What's new

### Two-way sync
- A new job kind, **Two-way sync** (`rclone_bisync`, rclone's `bisync`):
  two folders, each on a worker or on a remote, kept in step in both
  directions. New files, changes and deletions on either side spread to
  the other at the next run. It runs by hand or on a schedule
  ([two-way sync](../bisync.md)).
- **The first run of a pair resyncs on its own:** both folders are merged,
  nothing is deleted, and a file that differs keeps the newer version.
- **Conflicts keep both versions.** A file edited on both sides between two
  runs is kept twice, as `report.docx.conflict1` and
  `report.docx.conflict2`, on both sides; the job lists the conflicts.
  Optionally the newer, older, larger or smaller version, or one side's,
  wins; the other is still kept.
- **Safety checks:** a run that would delete more than half the files of a
  side (the limit can be set), that finds every file changed, an empty
  side, or, optionally, missing `RCLONE_TEST` check files stops before it
  changes anything. The job page explains which check stopped it and,
  where that helps, offers **Run once anyway**.
- **Resync now:** after changed filters or an error rclone cannot recover
  from, the pair fails with *Resync required* until someone runs a resync
  from the job's or the schedule's page.
- Two pairs that share a folder (the desktop's and the laptop's, on the
  same bucket path) never run at the same time: one waits for the other,
  marked *Waiting for folder*.
- A pair keeps its state on the worker that runs it, so its schedule
  targets one worker rather than a label. The worker removes the state of
  pairs that have not run for 180 days.
- New error codes: `resync_required`, `safety_abort` and
  `side_unavailable` ([API](../api.md)); hooks see them in
  `SYNCR_JOB_ERROR_CODE`.

## Known limitations

- The two paths of a pair may be at most 200 bytes together (rclone names
  its state files after them).
- Nested two-way locations (`R2:shared` and `R2:shared/sub`) and transfers
  into a two-way folder are not kept apart: their runs may overlap.
- One unreadable file stops its pair until it is fixed and the pair
  resynced.
- On backends without modification times (some WebDAV servers), an edit
  that keeps a file's size is not noticed.
- Two files whose names differ only in case collide on Windows and macOS.
- Changing a remote's settings other than its secret, such as a new access
  key ID after rotating an R2 token, makes the next run of its pairs a
  resync.
- Everything listed for [2.0.0](v2.0.0.md#known-limitations) still applies.

# Syncr 2.0.0

Syncr 2 is a rewrite of Syncr in Go: one **controller** (web UI, API,
Postgres) and any number of **workers** on your servers and desktops, which
run [rclone](https://rclone.org/) transfers and [restic](https://restic.net/)
backups for it.

## Before you install: a fresh start

**Syncr 2 does not read the data of the old Django version, and there is no
migration path.** Install it next to the old one or instead of it, and add
your remotes, jobs and schedules again. Your files and your existing restic
repositories are not affected: connect a repository that already exists
with its password and its snapshots are there.

## Install

- **Controller:** the [quick start](../../README.md#quick-start) runs the
  image `ghcr.io/zeptiny/syncr-controller` with Postgres from one compose
  file. Back up the database and `SYNCR_SECRETS_KEY`.
- **Workers:** in the web UI, **Workers, Add worker** shows one command per
  platform that downloads this release, enrolls the worker and installs it
  as a service ([Linux](../setup-linux.md), [Windows](../setup-windows.md)).
  A worker can also run in a container (`ghcr.io/zeptiny/syncr-worker`).

| Release file | What it is |
|---|---|
| `syncr-worker_linux_amd64.tar.gz`, `syncr-worker_linux_arm64.tar.gz`, `syncr-worker_windows_amd64.zip` | the worker |
| `syncr-controller_linux_amd64.tar.gz`, `syncr-controller_linux_arm64.tar.gz`, `syncr-controller_windows_amd64.zip` | the controller, with the web UI built in |
| `checksums.txt` | SHA-256 of every archive |

The archives carry GitHub build provenance:
`gh attestation verify <file> --owner Zeptiny`. Images are tagged `2.0.0`,
`2.0`, `2` and `latest`, for linux/amd64 and linux/arm64.

**Supported platforms:** workers on Linux (x86-64 and ARM64, with systemd,
or any Linux with `--no-service` or in a container) and Windows 10 or
Windows Server 2016 and newer (x86-64), as a service or per user. The
controller in a container on Linux (x86-64, ARM64), or as a binary, with
PostgreSQL 17. The web UI in a current Firefox, Chrome, Edge or Safari.

## What Syncr 2 does

### Workers
- One binary, installed by one command: `syncr-worker setup` enrolls the
  worker, downloads the pinned rclone 1.75.2 and restic 0.19.1 (checksums
  verified), writes its configuration and installs a systemd unit, a
  Windows service, or, without administrator rights, a per-user service.
- **Active** workers connect to the controller; **passive** workers are
  called by it over TLS with a pinned certificate, for machines the
  controller can reach but that cannot reach it.
- Jobs only touch local folders listed in the worker's `local_roots`.
  Remote credentials reach the worker only for the job that needs them,
  as environment variables of rclone and restic, never on a command line.
- A worker keeps the results of its jobs across restarts and connection
  losses and reports them when it is back.
- Labels group workers (for example `nas`); a schedule can run on the
  least busy online worker with a label.
- **`syncr-worker upgrade`** installs a newer release in place: it verifies
  the download, provisions the new tools, swaps the binary, restarts the
  service, and puts the old version back if the new one does not stay up.
  An outdated worker shows an **Outdated** badge and its upgrade command in
  the UI ([upgrading](../upgrade.md)).

### Remotes and jobs
- Remotes for S3 and compatible services, SFTP, Backblaze B2, WebDAV, a
  worker's local folders, and unions of remotes. Credentials are encrypted
  at rest and never shown again.
- **Test remote** lists a remote through a worker, also before saving it;
  **Browse** picks folders on a worker or a remote.
- **SFTP host keys:** a remote can pin the server's host keys, fetched from
  the server through a worker with one click (compare the fingerprints
  shown). A remote without them shows "Server not verified".
- Copy, sync and move jobs between remotes and worker folders, with live
  progress, a chart of the transfer, and the files that failed.
- **Time limits:** a job (or a schedule's jobs) can have a time limit;
  when it is reached the job is stopped on its worker and fails with
  `time_limit`, so the next job on the same repository can start. The
  controller can set a default for all jobs (`jobs.default_max_runtime`).
- **Hooks:** a job can run commands on its worker before it starts, after
  it succeeded or failed, and at its end: dump a database before a backup,
  stop and start an application's containers. The worker's operator defines
  them in `worker.yaml` under a name; users of the controller choose them
  by name and can change nothing about them. A failing hook fails the job
  (`hook_failed`), and the job's page shows how each hook went
  ([hooks](../hooks.md)).
- Cancelling or stopping a job stops every process it started.

### restic backups
- Create a repository on any remote, or connect one that exists. Its
  password is encrypted at rest and never shown again: keep your own copy.
- Backup jobs of a worker's folders (on Windows, optionally from a volume
  snapshot), retention with prune, and check jobs.
- Browse a repository's snapshots and restore all of a snapshot, a folder
  or selected files into a folder of a worker. Restores never overwrite
  existing files unless you choose to.
- Jobs on one repository run one at a time, in order.
- Deleting a repository forgets it; deleting its data is a separate,
  confirmed choice. Details: [restic backups](../restic.md).

### Schedules
- Cron expressions with a time zone and daylight-saving rules, a preview of
  the next runs, on one worker or on a label.
- Policies for missed runs (run late, up to a limit, or skip) and for
  overlap (skip, queue or allow). Runs missed while the controller was
  down merge into one.
- A schedule pauses itself, and says why, when its worker, remote,
  repository or owner goes away.

### Notifications
- Contacts on Discord, email (your SMTP server) and webhooks (signed per
  Standard Webhooks, or in Slack's format), linked to schedules and to your
  manual jobs, per event: succeeded, failed, interrupted, missed.
- Notifications are stored before they are sent and retried for about an
  hour; each contact has a delivery log. They may go to LAN addresses but
  never to loopback, link-local or cloud metadata addresses by default.

### Accounts, API and dashboard
- Users with passwords (argon2id), sessions, a first-run setup code in the
  controller's log, and administrators who manage users and workers.
  Remotes, repositories and schedules belong to their owner.
- Personal API tokens for scripts; everything the UI does goes through the
  same Connect API.
- A dashboard of the last 24 hours, 7 or 30 days: jobs, bytes moved,
  success rate, running and queued jobs, missed runs, upcoming runs and
  worker health.

### Operating the controller
- Configuration in YAML or `SYNCR_*` environment variables; unknown keys
  are refused.
- The schema is migrated at start. **One controller runs per database:**
  a second one waits until the first stops, then takes over.
- A job's progress chart is kept for 30 days after the job finished
  (`jobs.sample_retention`); the job and its totals are kept.
- HTTPS directly or behind a reverse proxy, with a health check for
  containers (`syncr-controller -healthcheck`).

## Known limitations

- No builds for macOS or Windows on ARM.
- rclone's wrapper backends (crypt, alias, chunker) are not offered yet.
- Job history and schedule runs are kept forever; only the progress charts
  expire.
- Releases are checksummed and carry build provenance, but are not signed.
- Fetching SFTP host keys does not go through a remote's proxy settings,
  and is trust on first use: compare the fingerprints with the server's.
- A worker that runs per user on Windows runs only while that user is
  logged on, and cannot use volume snapshots.
